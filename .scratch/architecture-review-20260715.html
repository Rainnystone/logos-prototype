LOGOS — Deepening Opportunities

A scan for shallow modules, smeared seams, and duplicated invariants across the authoring, runtime, sidecar, and API layers. Each candidate is a refactor that would turn shallow modules into deep ones — concentrating complexity behind a small interface, improving locality and testability.

Vocabulary: This report uses the deep-module design vocabulary — module, interface, depth, seam, adapter, leverage, locality. A deep module hides a lot of behaviour behind a small interface. A shallow module has an interface nearly as complex as its implementation. The deletion test: if you delete the module, does complexity vanish (pass-through) or reappear across N callers (earning its keep)?

1. Bridge per-section handler table

src/authoring/persistence/bridge.ts · 960 lines · 1 public export

Strong

Files

  • src/authoring/persistence/bridge.ts
  • src/authoring/persistence/repository.ts
  • src/authoring/sections/control-modules.ts
  • src/authoring/sections/scene-phase-authoring.ts
  • src/authoring/sections/worldbase-cast.ts
  • src/authoring/contracts.ts

Problem

The bridge is the deepest module in the authoring layer — one saveSectionDraft() function hides ~660 lines of behavior. But the depth is disorganized: the per-section dispatch (extract → validate → render → persist → restore) is a hand-rolled vtable spread across 400 lines. The transactional rollback pattern is duplicated 5 times with subtle per-section variation. Adding a sixth section means editing four files and copy-pasting a rollback block.

Solution

Introduce a per-section handler registry: each entry is { extract, validate, render, persist, restore, readOriginal } keyed by sectionId. The bridge becomes a generic dispatcher that calls withRollback(handler, target, request) — collapsing ~180 lines of duplicated rollback into ~40. The "section kind" concept gets a single owner.

Benefits

  • Locality: Adding a section becomes a single-file change instead of a four-file change.
  • Leverage: The withRollback helper is tested once; all sections inherit the guarantee.
  • Testability: Handlers can be injected in tests — the bridge's interface becomes its actual test surface, not its import graph.
  • Removes dead code: The vestigial catch (earlyResult) at line 903 and the unreachable check at line 580 become impossible.

Deletion test: The bridge earns its keep (complexity reappears in PlayWorkbench if deleted). But the 5× rollback duplication and 3× private extractors fail the test — deleting them and using the registry concentrates complexity rather than moving it.

3. Extract useSectionSave hook from EditWorkbench

src/app/edit/EditWorkbench.tsx · 917 lines · 3 near-identical handlers

Strong

Files

  • src/app/edit/EditWorkbench.tsx

Problem

Three submit handlers — handleWorldBaseCastSubmit (~100 lines), handleScenePhaseSubmit (~100 lines), handleControlModulesSubmit (~110 lines) — share ~80% structure: set saving → fetch PATCH → remember result → if applied, update state → if blocked/failed, escalate to coordinator → catch → finally. The coordinator-escalation rule is encoded 3 times. The component also leaks an implementation detail via didPersistAuthoringState() — it string-matches changedFiles.includes('authoring-state.json').

Solution

Extract a useSectionSave(sectionId, draftState, savedState) hook returning { submit, reset, isSaving, status }. The hook owns the fetch → remember → coordinator-escalation pipeline. Additionally, add persistedAuthoringState: boolean to SaveResult so the component stops reaching into changedFiles.

Benefits

  • Locality: The coordinator-escalation policy lives in one hook, not three copies.
  • Testability: The hook can be tested in isolation — no full React render needed.
  • Leverage: A fourth section gets the save pipeline for free.
  • Fixes leaky abstraction: didPersistAuthoringState becomes a field on SaveResult.

4. Extract createPackageWithOptionalBootstrap orchestrator

src/app/api/authoring/packages/route.ts · 210 lines in HTTP handler

Worth exploring

Files

  • src/app/api/authoring/packages/route.ts
  • src/story-packages/scaffold.ts
  • src/agents/weaver/repository.ts
  • src/agents/gossipelog/bootstrap.ts

Problem

The package-creation route orchestrates 5 domains: scaffold → weaver summary → gossipelog bootstrap → fallback reconciliation → warning append. Domain rules (reconcileFallbackPendingSummary, appendBootstrapPendingWarning) live in the HTTP layer. The "create package = scaffold + weaver + bootstrap + fallback" ordering is a business rule with no home. The route strips adapterConfig for zod, then re-extracts it from the raw body — a strip/re-extract dance.

Solution

Extract a createPackageWithOptionalBootstrap(input) module that owns the 5-step pipeline and returns a structured result. The route becomes a true HTTP adapter: parse body → call orchestrator → map result to status.

Benefits

  • Locality: The "what happens when you create a package" rule lives in one module.
  • Testability: The orchestrator can be tested with mocked scaffold/bootstrap without HTTP.
  • Leverage: Another entry point (CLI, batch import) calls the orchestrator, not the route.

Problem

Retry ceiling = 3 is duplicated across 4 modules with different names. The orchestrator's rewrite loop and the tracked-adapter's retry counter both depend on this ceiling but have no shared constant. If one changes, the others silently desynchronize.

Solution

Two shared constants: PHASE_BEAT_COUNT (already exported, just needs to be imported everywhere) and LLM_RETRY_MAX_ATTEMPTS (new, shared by router/collapse/settlement/audit-resolver). Low effort, high safety.

Top recommendation

Start with Candidate 7 (delete dead shallow modules) — it's zero-risk and removes navigation friction immediately. Then tackle Candidate 2 (provider-utils extraction) — the most unambiguous win, with ~140 lines of verbatim duplication.
