Recommended Roadmap

基于当前仓库现状，我建议把原来的 4 条路线重组成 4 个阶段，而不是继续把 3 / 4 / 5 / 6 / 7 生硬地并列。

先回答你的核心判断

角色关系可视化 横跨两层。

3a 关系状态查看 属于 角色模型 / 角色页，因为它依赖角色 ID 和关系文件读取。

3b 关系变化连续性 属于 session continuity，因为它要把 workbench 里刚跑出来的状态无损带到 editor。

所以不建议把“关系”整包塞进 C；最好拆成 静态查看 和 运行中连续性 两部分。

Phase 1: Model & Surface

先做

1. `世界与角色` 拆成 `世界` / `角色` 两页

2. 地点结构化，给地点稳定 ID

3. scene 能选择可调用地点

4. 角色页显示当前持久化的关系状态

5. agent 管理窗口先做只读外壳，至少能看见 `gossipelog agent` 和 skills

Phase 2: Session Continuity

第二步

1. workbench 切到 editor 不清零

2. 增加显式 `Reset Workbench`

3. 把“作者上次离开处继续”做成 session 恢复

4. 把关系变化的“当前进度视图”接到角色页

Phase 3: Package & Storyline

第三步

1. 故事包管理

2. 一个故事包内多条故事线 / 多份进展

3. workbench session 与 storyline 绑定

4. 作者恢复点不再只是“最后编辑页”，而是“回到对应故事线进度”

Phase 4: New Agents

最后扩展

1. 外部前序故事导入 agent

2. agent 管理窗口从只读外壳升级到真正管理面

3. 导入结果落到选定故事线，而不是污染主样例包

为什么我不建议先做 C / D

C 的真实难点

  • 当前 workbench 状态几乎都在页面内存里
  • 要保留的不只是文本，还包括状态快照、阶段位置、beat 历史、关系层、可能的后台刷新
  • 如果先做，而角色 / 地点模型还没稳定，后面 session 结构很容易返工

D 的真实难点

  • 它不是多一个页面，而是引入新的顶层对象
  • 会碰目录结构、加载逻辑、保存目标、故事线身份、导入落点
  • 这是当前 7 项里牵扯面最广的一块
我的推荐顺序

先稳定数据模型与表面，再做 跨页连续性，然后才做 多故事线，最后再把 新 agent 接进来。

换成一句话就是：先让世界对象和角色对象长稳，再让故事跑得不断，再让同一包里能有多条进度，最后才让导入 agent 有可靠落点。

下一步只确认一个问题

如果你认可这次重组，我下一步就不再问“先做 A/B/C/D 哪个”，而是改问：Phase 1 里，`世界/角色拆页 + 地点结构化` 和 `agent 管理只读外壳`，你想先把哪个放在最前面？
